# 需求决策文档
生成时间：2026-06-09
需求名称：听写宝（tingxiebao）— 中小学生英文听写/听说微信小程序

## 真正的问题
**用户是谁：** 需要帮孩子做英文听写/听说练习的家长，尤其是两类人——
1. 忙、没时间每天陪练的家长（如用户本人，有两个孩子、分别初二/四年级）
2. 英语水平不好、不敢开口、无法判断对错的家长

**用户在什么处境：** 传统听写需要家长全程参与——报中文单词、听孩子回答、判断对错、纠正。一次完整的听写练习耗时 15-30 分钟，高频（几乎每天），且家长的英语水平直接决定了练习质量。

**根因：** "家长作为人工裁判"是这个场景的瓶颈——换个家长就换一种标准，换个时间就没有反馈。解决方式是把这个角色自动化。

**核心价值假设：**
同一个单词表，第二遍错的比第一遍少一半以上 —
如果做不到，说明错题重练机制没有产生学习效果，产品的基础不成立。

## 影响范围
- 上游：教材版本数据（至少覆盖合肥地区人教版）、用户自传 Excel 词表
- 下游（用户行为的下一步）：从练习到看到结果、从结果到错题重练、从重练到掌握
- 相关功能：语音播报（中文TTS）、语音回答（英文ASR + AI评判）、打字回答、错题本、练习记录
- 关键指标：第二遍错误率下降幅度、日活使用频次
- 最可能的失败原因：不够简单——孩子打开要点三四下才能开始练，用了两次就不用了
- 需要同步的 stakeholder：暂不涉及（个人项目阶段）

## 时机判断
- 为什么是现在：用户两个孩子分别处于初二和四年级，英文听写需求真实且持续；ICP 备案已在审核中（预计 2-3 周）；用户本人是程序员，有能力自己实现
- 放弃了什么：备案等待期直接开发 Web 版作为先行验证，放弃"一步到位上小程序"的路径

## 确认的前提
1. 孩子愿意在没有家长监督的情况下，自己打开网页/小程序完成听写练习
2. 语音回答（Web Speech API）在 MVP 阶段就做，打字输入同步支持
3. 按课本单元选词 + Excel 上传自定义词表，两种方式覆盖 80%+ 家长需求
4. 浏览器内置 SpeechSynthesis（中文播报）准确度够用，不需要付费 TTS
5. ICP 备案下来之前，先在 ECS 上用 IP+端口跑 Web 版，验证核心体验

## 方案选项

**技术架构：前后端分离，Vue 3（Web前端）+ Node.js/Express（后端API）+ PostgreSQL/MySQL（数据库），部署阿里云 ECS。**
后端 API 与微信小程序共享，Web 和小程序只是两个不同的前端客户端。

## 决策建议
- 做
- 分两步：Web 版先行（2-3 周MVP） → 备案下来后加小程序前端
- 理由：等待备案的窗口期不浪费，用 Web 版在自己孩子身上验证核心闭环

## 验收标准
- 成功指标：同一个单词表，第二遍错题数 ≤ 第一遍错题数的 50%
- 失败指标：孩子打开两次后再也不主动使用
- 复盘时间节点：Web 版上线后两周

## 对话中发现的盲区
- 产品一开始叫"听写宝"，但实际场景不是纯听写，是"中文播报→英文回答（语音/打字）"，更接近中译英口语练习
- 语音识别不准不是产品的缺陷，而是产品的功能——逼孩子纠正发音
- 用户最初描述的"解放自己时间"背后，更深的需求是"英语不好的家长帮不了孩子"——后者是一个更大的用户群

## 思维观察
- 用户说"把问题变成功能"——语音识别不准就让孩子重说——这种思路说明他在从用户处境出发设计，而不是堆砌功能
- 从"我自己家孩子用"到"英语不好的家长也会用"这个洞察，比最初的"解放家长时间"更准确地定义了产品的核心用户群
